## 产品陈述

Agent Platform 为一个用户提供长期、统一的协作界面，在同一处讨论需求与架构、查看多个隔离 Workspace
的进度与状态图，并协调不同角色的 Agent。图形与文本说明共同帮助用户掌握当前工作、依据和待决事项。

平台框架组织整个工作生命周期：Agent 承担规划、集成、语义审查与解释，工具承担可机械化的采集、检查与
更新，框架依据规则维护持久状态、验证和展示。进度更新是正常执行路径的一部分，不依赖额外的人工或模型提醒。

`coding-agent` 继续作为 Execution Kernel。Agent Platform 不重写其模型循环、工具、安全或单次
Run 恢复能力。

## 问题来源：Context、状态与人的注意力

本产品从一次执行的 Context 与跨执行的状态如何协作出发：Context 是模型本次判断能使用的材料，需要保持
相关、有效且有界；Goal、角色责任、计划、执行事实与决定则需要跨 Run 和 Agent 持续维护。长期系统还要管理
这些状态的版本、适用性和生命周期，并把相关部分送回每次执行与人类界面。

当这些责任集中在一个不断增长的会话中、缺少框架约束时，会出现：

- 长任务中的 Todo 与实际进度脱节；
- Context、Run 或 Agent 更换后丢失工作前沿；
- 用户询问状态会打断正在执行的 Agent；
- 多 Agent 的依赖、写入冲突和完成依据不可见；
- Worker 的“已经完成”容易被误当作系统完成；
- 项目架构随长期开发漂移，却缺少持续对账和决策记忆。

这些现象共同指向 Context 管理、外部状态、框架控制和协作反馈的工程问题。用户需要在有限注意力下理解
状态并参与需求和架构取舍。推导与 OpenAI／Grok Bot 实践的适用范围见 [需求来源索引](dev_docs/product/README.md)。

## 产品承诺

用户能够：

1. 在同一协作界面查看和切换多个 Project/Workspace；
2. 创建 Goal，通过状态图和文本说明查看由框架维护的计划、进度、阻塞及其依据；
3. 查询或讨论正在进行的工作，而不必打断源 Worker；
4. 在安全边界暂停、继续、取消或修改目标；
5. 看见 Agent 分工、当前 Run、Evidence、Handoff 和失败原因；
6. 与秘书／参谋 Agent 共同确立需求、形成架构方案并讨论变动，理解关键选项、影响与已接受决定；
7. 在 Run、Context 或 Agent 更换后继续工作；
8. 追溯当前架构为什么如此，以及哪些漂移尚未处理；
9. 在需要人选择的需求／架构取舍、风险授权和未预授权变化上决策；普通已授权工作由框架与 Agent 闭环推进，并提供可见结果。

## 产品能力

### 状态真实性

Goal、Runtime Task、Attempt 和 Run 的当前状态，以及 Evidence、Decision 和状态变化的来源，由框架持久维护。
当前状态可以按规则推进，历史事实和证据保留可追溯记录。工具报告确定性结果，Agent 提供语义判断，框架校验
适用性并提交状态转换。Todo、状态图、Plan Matrix、Dashboard 和 Timeline 据此投影。

工程上必须证明：重复输入不重复写入、过期依据不能推进当前状态、中断后可以恢复、视图可以重建、投影延迟可见。
相关候选机制见 [ARCHITECTURE](ARCHITECTURE.md) 与 [状态实现复核](dev_docs/design/human-framework-role-review.md)。

### 连续执行

工作不属于某个模型 Context。新 Run 或新 Agent 可以从持久状态和有界 HandoffPacket 接续。

### 角色协作

规划／集成者负责理解已明确的目标、拆分工作、整合结果、识别冲突与返工；执行者／Coder 在有界 Context 和
权限内实现。秘书／参谋参与人与 Agent 的协作，并与规划／集成职责共同承担分工、耦合分析、测试设计和结果协调。
角色名称不是封闭枚举，可按任务配置短生命周期角色，仍由框架绑定权限、预算与退出条件。
这些协调职责可按需要拆分 Agent 实例与 Context；普通已授权协调通过框架直接驱动执行，必要取舍才升级给人。

平台按真实依赖、角色所需信息和权限派发工作，维护执行与状态。并行、只读和写入权限是执行机制，不能代替
角色定义；MVP 的核心是证明规划、执行、集成与验证闭环。同一 checkout 的写入安全仍需验证。

### 证据驱动完成

Worker 只能提交 CompletionClaim。平台组合静态、运行、测试与语义 Evidence，再按当前义务判断 Task
和 Goal 是否完成。

### Human Collaboration

主对话、状态图、面板、提醒、查询、参谋和控制入口在同一界面中协作，事实展示具有共同来源，语义说明标明
其事实依据。人和 Agent 共同明确需求、参与架构生成与变更讨论；系统呈现选项、影响、决定和执行反馈，确保人知情。
知情不等于每步审批：普通已授权实现和验证由框架与 Agent 闭环完成。

### 架构治理

架构治理包括最初建立、持续对账与变更演进。秘书／参谋协助人形成需求和架构方案，已接受决定进入版本化规范
与 ArchitectureBaseline。此后与实际代码对账；局部、确定、可逆且已授权的漂移进入正常修复流程，重大或含糊
变化由人和 Agent 讨论选项、影响与迁移方法，并记录决定和反馈。

## MVP 必须证明

- 单用户、单机管理多个隔离 Project/Workspace；
- 一个 Goal 首版绑定一个 Workspace；
- Goal → Runtime Task → Attempt → Run 的状态可重建；
- Worker A 的 Run/Context 结束后，Worker B 能仅靠持久状态和 HandoffPacket 接续；
- 规划／集成与执行角色依靠有界输入、结果交接和框架状态完成闭环；并发和写入安全有独立验证；
- Task 和 Goal 不能因自称完成、空计划或过期 Evidence 变绿；
- 用户可查询、暂停、继续、取消和安全修改目标；
- 同一界面以图形和文本展示 Goal、Task、Agent、Timeline 与依据，状态模型可直观查看；
- 人能与秘书／参谋共同明确需求、参与架构建立或变更，并获知决定及执行影响；
- 一次架构漂移可以被发现、解释并进入修复或决策路径；
- 崩溃恢复不把未知副作用猜成成功或失败。

## MVP 非目标

- 多 Writer 同时修改同一 checkout；
- 跨 Project/Workspace 的自由 Agent 通信；
- 跨机器共识、高可用或多租户权限系统；
- 通用工作流 DSL；
- 完整 IDE；
- 无限自主 spawn；
- 让完整 transcript、Memory 或 RAG 独立承担进度与完成判定；它们可以辅助 Context 检索，状态模型及其图形化展示属于 MVP；
- 为目标架构中的每个方框提前创建目录和抽象。

## 成功标准

- 状态查询准确率为 100%；
- 每个 completed Task 都能追溯到当前适用 Evidence；
- 依赖未满足、revision 过期或写入冲突会被确定性拒绝；
- Handoff 后不需要重放完整 transcript；
- 同一真实任务与单长会话基线相比，成功率不下降；
- 用户必要决策与无效打断分别度量，并记录总时间、Token、重复探索和恢复结果；
- 任一失败可以归因于计划、执行、验证、权限、预算、环境或恢复。

## 产品裁决与复核状态

已有边界与本次用户修订（不代表整套 P0／P1 已批准）：

- Agent Platform 是独立产品层；
- Human Collaboration 可以主动提醒、讨论和安全打断，但不能直接改写状态；
- 首版管理多个隔离 Workspace，领域模型通用、执行场景 coding-first；
- A→B 接续及写入隔离仍需验证；旧“双只读并行”不再单独代表角色协作门禁，G3 的完整角色场景已写入 MVP 草案，阶段批准另行记录；
- 验证默认由系统与 Reviewer Agent 闭环；人参与需求和架构生成、重要取舍、主观事实及授权；
- Module 是空间责任，Stage 是成熟度视图，真实依赖和运行 phase 分开。

精确状态 schema、Reducer 优先级和 Provider 选择属于 Module/Interface 与 Ticket，不进入本文。
