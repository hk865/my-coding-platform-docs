# Agent Platform 性能诊断报告（2026-09-18）

## 诊断范围

本报告对应已接纳的 snap-30／real31，产品提交为 `58c9ada73966711437c5fcd3d8f8fb92f3dca210`。诊断脚本和复制数据仅保存在 `.local` 或临时目录，没有修改权威场景数据。状态读取基准关闭了模型执行。

本报告采用 **99% 提示词缓存命中率**作为优化目标。历史数据没有显示近期大幅下降，但这不代表当前命中率合格：real31 只有 77.48%，距离目标仍差 21.52 个百分点。

## 实测结果

### 真实模型负载与提示词缓存

real31 完成 90 次模型响应，输入 2,657,892 Token，输出 197,383 Token，其中缓存输入 2,059,392 Token，加权缓存命中率为 **77.48%**。

按 99% 目标计算，应有约 2,631,313 个输入 Token 命中缓存；本次还缺少约 **571,921 个缓存命中 Token**。当前缓存效率明确不达标。

| 调用类型 | 调用数 | 输入 Token | 缓存 Token | 加权命中率 | 单次最低命中率 |
|---|---:|---:|---:|---:|---:|
| Query | 53 | 1,567,568 | 1,185,536 | 75.63% | 15.60% |
| Reviewer | 26 | 712,775 | 529,536 | 74.29% | 31.35% |
| Coding | 5 | 81,062 | 70,656 | 87.16% | 47.54% |
| Coordinator Report | 6 | 296,487 | 273,664 | 92.30% | 24.49% |

Query 与 Reviewer 合计 79 次调用、2,280,343 个输入 Token，是缓存损耗的主要来源。协调报告总体较高，但仍未达到 99%，且单次最低只有 24.49%，说明请求之间存在明显差异。

在 26 个已归档真实场景中，共有 829 次响应、17,696,912 个输入 Token、13,763,840 个缓存 Token，加权命中率为 77.78%；单场景范围为 71.53%–84.76%。最早五个场景为 74.06%，最近五个场景为 77.06%。因此：

- 没有证据表明命中率近期突然大幅下降；
- 长期命中率一直处于约 78% 的低位；
- 按 99% 目标，现状属于持续性性能缺口，而不是合格状态。

请求输入中位数为 25,535 Token，P90 为 51,309；输出中位数为 758 Token，P90 为 6,016。单请求缓存命中率中位数为 76.19%，P10 为 30.68%，P90 为 97.35%，没有完全零命中的请求。

现有证据更符合“请求前缀或调用分组不够稳定，动态事实重复进入大段上下文”的问题，不能直接证明 provider 缓存系统失效。角色、Run、版本、权限、材料和事实块会随调用变化；Query 与 Reviewer 又占绝大多数输入量，因此部分公共内容命中后，整体仍被动态区段和新调用拉低。这个判断仍是待请求级公共前缀数据验证的架构假设，不能写成最终根因。

### real31 持久数据上的状态与 currentness 路径

基准使用 real31 持久数据副本，并关闭模型执行。

| 读取方式 | 样本数 | 平均耗时 | 范围 |
|---|---:|---:|---:|
| `/api/state?view=overview` | 8 | 40.0 ms | 30.7–59.1 ms |
| 包含 Query currentness 的完整 `/api/state` | 8 | 6,996.5 ms | 6,888.2–7,145.4 ms |

完整读取约为概览读取的 175 倍。逐回答 applicability 测量显示，七条可通过廉价条件判定失效的回答耗时 11–35 ms；另四条耗时 6,756–6,969 ms。昂贵分支通过廉价版本检查后，会重新构建 collaboration 和 verification 事实。

同一小型候选项目上的直接来源操作在文件系统预热后并不昂贵：

- Query 来源 revision：首次 16.2 ms，之后 2.1–3.1 ms；
- Verification 来源捕获：首次 15.8 ms，之后 3.2–4.1 ms。

因此，real31 中约 7 秒的 currentness 耗时主要来自组合层重复重建事实和读取权威存储，不是小型候选工作区单次哈希本身。

### Agent Platform 产品工作区的来源捕获

- 一次 `QueryWorkspaceSourceReader.sourceRevision`：112,022 ms，结果为 ready；
- 一次 `VerificationWorkspaceReader.capture`：130,095 ms，结果为 incomplete。

候选快照会排除 `.git`、`.platform-runtime`、`node_modules`、`dist`、`coverage`、`test-results` 和 `.cache`，但不排除 `evidence`。当前工作树约有 9,269 个已跟踪 evidence 文件，另有约 41,108 个未跟踪 evidence 文件。Verification 会捕获候选两次并与 Git 比较，因此运行证据目录主导了遍历与哈希成本。这是已实测的工作区策略和模块组合性能问题。

### ReadModel 固定规模路径

现有 material-access 性能基准通过。在 1,024 个事件下：

- 内存适配器 advance 8.44 ms，list 0.086 ms，精确 candidate 0.203 ms；
- SQLite 适配器 advance 59.45 ms，list 4.67 ms，精确 candidate 1.91 ms；
- SQLite prepare 次数随事件线性增长，1,024 个事件对应 1,025 次 prepare。

该路径不是当前主要瓶颈。另有一个复杂度风险：SQLite 独立审阅投影会在每个审阅事件上读取并解析整个 `independent_review_projection` 表，候选复杂度为 O（事件数 × 累计审阅数）。实际严重程度仍需专门增长基准，当前不能写成主要运行瓶颈。

### MemoryContextCompiler 选择缓存

在 5,000 次内容稳定且完全相同的 select 中，有 4,999 次结果 digest 相同，可作为复用候选；但编译器仍执行了 5,000 次 `localProfile` 读取、5,000 次 profile-scope 读取和 5,000 次 project-scope 读取。

当前缓存会先验证 revision 和来源，再复用选择结果。它保证复用正确性，但不是避免底层 I/O 的缓存。这会削弱缓存对总耗时的改善，也说明最终 digest 相同不能直接视为有效命中。生产路径尚未暴露细分命中、前缀复用和失效原因指标。

## 瓶颈优先级

1. **提示词缓存复用不足。** real31 仅 77.48%，距离 99% 目标 21.52 个百分点；Query 与 Reviewer 是最大输入来源，也是命中率最低的两类主要调用。
2. **Query currentness 重复组合。** ContextCompiler、VerificationEngine 和权威存储之间重复重建事实；完整状态约 7 秒，概览约 40 ms。
3. **WorkspaceReader 快照范围过大。** 产品自身工作区捕获耗时 112–130 秒，运行 evidence 被纳入扫描。
4. **真实模型编排调用数量和上下文体积。** 90 次调用与大输入会放大每个百分点的缓存损失。
5. **SQLite 独立审阅投影增长风险。** 代码路径存在复杂度风险，但尚未实测为当前主要瓶颈。
6. **开发反馈周期。** 长恢复和浏览器套件影响工程吞吐，但应与产品运行时瓶颈分开统计。

## 建议的改进方向

1. **先补缓存可观测性。** 每次模型请求记录角色、Run ID、输入 Token、缓存 Token、稳定前缀 digest、动态尾部字节数、系统提示 digest、Skill digest 和工具 schema digest。只记录摘要和长度，不能保存密钥或额外复制敏感提示内容。分别报告冷启动与可复用热调用，热调用以不低于 99% 为目标；冷启动不能用来掩盖热调用低命中。
2. **定位前缀变化来源。** 比较同角色相邻请求的稳定区段和最长公共前缀，确认是系统提示、工具 schema、角色 Skill、材料排序、版本事实还是 Run 身份导致缓存边界提前终止。
3. **重排上下文，但不削弱事实边界。** 候选方案是把稳定系统规则、角色 Skill 和工具定义放在稳定区段，把按请求变化的事实、材料、版本和用户输入放到后续动态区段。实施前必须用请求级 digest 实验证明改善。
4. **按版本复用不可变事实制品。** 对同一 scope、权限、来源版本和 freshness witness 下的事实快照按 digest 复用；权限变化、撤权、来源更新或 freshness 变化必须失效，不能用缓存绕过 currentness 检查。
5. **拆分 Query 事实清单和 applicability 验证。** 每次 observation 只构建一次 scope/version 事实快照，再用该快照验证多条回答；保留异步读取前后的必要复核，移除同一 observation 内重复重建。
6. **建立版本化来源 manifest。** 由 WorkspaceReader 负责，只有 root identity、策略、权限 scope 和 observed source version 全部一致时才复用。运行输出和 evidence 是否参与捕获应成为明确工作区策略，不能简单硬编码为所有项目一律排除。
7. **保持 UI 概览读取走廉价路径。** React 默认概览已经使用 overview；旧 UI 每 2.5 秒轮询完整状态，应改为 overview 或按需读取回答 applicability。
8. **先补独立审阅投影增长基准，再决定 ReadModel 改造。** 避免把尚未测量的风险扩大成无边界重构。

本次发现不支持引入 Redis。当前问题是本地重复工作、快照范围、上下文前缀不稳定和缺少版本化复用。远程缓存不会自动消除这些重复，反而会增加 freshness、撤权、来源变化和不可用行为的处理成本。
