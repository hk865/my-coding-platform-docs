# Agent 生命周期、Session 复用与 ContextCompiler 职责收敛建议

日期：2026-09-18。状态：用户提出的后续设计方向与候选方案，尚未冻结实现契约。本次授权是积累到原始文档仓库，不是启动源码重构。本文不改变 I 阶段既有接纳范围。

## 来源与问题

用户在本次对话提出：探索项目形成的认识应成为可复用工作状态与记忆来源；Agent 完成探索或任务后，可以继续承担相关修改，也可以为其他 Agent 提供帮助。负责某模块的身份无需随会话重建而改变。容量达到上限时允许压缩或更换 Session，保留适用记录，避免错误认识继续误导。用户希望通过角色卡片查看其正在做什么。

相关实测见[中文性能诊断](2026-09-18-performance-diagnosis.md)。该诊断记录 real31 提示词缓存加权命中率 77.48%、完整状态读取约 7 秒、产品工作区来源捕获约 112–130 秒。这些是指定数据集与环境下的结果，不自动证明 Agent 生命周期是全部性能问题的根因。

## 与已有规范的关系

[ARCHITECTURE](../../ARCHITECTURE.md) 已规定角色绑定、跨 Run 工作责任、Session 轨迹、接续与内核压缩能力；[Context 生命周期](../interfaces/context-lifecycle.md) 已区分 WorkContext、ContextBundle、Run，并规定暂停、恢复、压缩、转交和后续任务继承。因此不能把本次建议表述为“原规范完全没有考虑生命周期”。

本次需要推进的是：核对这些原则在真实产品中的落实程度，补齐可观察的生命周期管理、相关 Agent 选取、连续 Session 复用与增量刷新。准确实现状态仍以[模块状态](../../human/module-status.md)及后续源码核对为准；本文不把未经核对的项目列为已确认缺陷。

## 用户认可的设计方向

持续管理有身份和负责范围的 Agent，让其探索、执行、返工和协作经历可以复用。身份持续不要求进程常驻，也不意味着所有工作共享一个无限增长的上下文。

| 概念 | 候选职责与边界 |
| --- | --- |
| Role | 职责、能力与权限规格；与具体执行身份分开 |
| Agent | 稳定工作主体，关联负责范围、角色绑定、工作经历与当前状态 |
| WorkContext | 连贯工作的责任与前沿，可跨 Run；复用现有概念，避免另造重复身份 |
| Session | 连续交互、工具反馈与执行上下文的载体，可暂停、恢复、压缩或更换 |
| Run | 一次具体执行，保留独立授权、租约、结果和恢复边界 |
| 执行记忆 | 从工作轨迹形成、具有来源和适用范围的可复用认识 |

稳定 Agent 身份与 WorkContext 的精确基数关系、Session 标识及持久字段留到消费者设计时确定，不预先增加独立 Module 或平行状态系统。

## 生命周期与选取

候选流程：相关任务到达 → 查找具有相关负责范围和探索记录的 Agent → 核对权限、源码版本、忙闲状态、Session 能力与容量 → 继续原 Session、增量刷新或用新 Session 接续 → 持久记录实际路径。

例如权限模块维护 Agent 再次收到修改任务，可以继承其对模块的认识，加载上次观察版本之后的变化。其他 Agent 求助时，优先读取它的适用报告，必要时通过受控协作取得补充；不能直接共享隐藏上下文或借用旧授权。

待验证行为包括等待后恢复、相关返工、跨任务继承、并发求助、重启恢复、压缩和退休。复用决策需要可解释：为何选中该 Agent、复用哪些材料、哪些材料因过期或撤权被排除。不得以固定常驻 Agent 数量或新增进程管理器代替需求分析。

## Session 作为状态和记忆来源

需要区分三类信息：

- 工作状态：已探索文件及版本、工作前沿、等待事项、工具执行与未解决问题；应可持久追溯。
- 可复用认识：模块关系、经过验证的结论、失败路径及原因；携带来源、版本、权限、适用范围和纠正关系。
- 权威事实：完成、授权、正式决定等仍由既有责任模块的持久记录决定，Session 中的陈述不能替代它们。

错误内容可以退出后续选材，保留原始记录及纠正链供追溯。压缩不能把推断变成事实、丢弃关键不确定性，或把历史授权带入新任务。相同模块名称也不能绕过项目隔离。Agent 认识发生更新不自动成为跨项目用户记忆。

## ContextCompiler 职责收敛

ContextCompiler 重点服务首次启动、恢复、材料变化、压缩后重建及新 Session 接续。连续工作应评估增量材料更新，避免每次重新组装全部认识。生命周期策略决定何时继续、刷新或重建；ContextCompiler 提供有界、可追溯的选材结果，不承担选人、调度和正式状态归约。

候选分责沿用现有架构：Control 管理策略与授权，Dispatch 落实唯一派发，WorkerRuntime 适配内核 Session 能力，Data 保存记录并提供检索与材料编译。是否需要细分内部接口，以实际消费者和测量结果决定，不在本建议中直接修改 Module DAG。

复用仍需处理撤权、来源变化、freshness 和未知外部副作用。目标是减少重复读取与重建，不能删除不同时间点必需的复核。

## 用户界面

角色卡片应能展示具体 Agent 的负责范围、当前工作、忙闲或等待状态、最近探索版本、关联 Session、待处理事项和可追溯记录。继续使用时说明实际是恢复原 Session 还是新 Session 接续。显示内容应来自持久状态及明确 freshness，不能用模型自述冒充正式进度。

## 性能目标与验证

99% 是用户提出的缓存优化目标，不是已经证明适用于所有请求的行业标准。应同时报告整体 Token 加权命中率、冷启动、可复用热调用、角色和任务类型；新增输入和冷启动必须纳入总体成本，不能通过选择口径获得达标结论。Session 复用本身不保证 provider 缓存命中。

后续用同一项目、任务和模型配置比较当前流程与复用方案，记录探索重复次数、来源扫描量、事实快照重建次数、上下文组装耗时、输入与缓存 Token、模型调用数和端到端耗时。比较至少包括首次探索、同模块后续修改、源码变化、撤权、并发求助与新进程恢复，并验证权限隔离、唯一调度及未知动作不盲目重放。

### 用户原话

> 还有就是把这个……然后我觉得这是个架构问题，因为角色的生命周期，以及角色的管理，似乎并没有得到产品文档和架构文档里面的解释，没有落实，就根本没有考虑到这一块。如果有生命周期，然后 Agent 的 Session 也视为 States 的一部分，因为你探索一个项目，你要得到相关的 Context，就需要 Agent 去探索。然后这些 Agent 的探索本身就是一个非常好的 States 的来源，也是记忆的来源。所以说角色的生命周期，就比如说它探索完之后，知道了这些文件，那么就可以复用这个 Agent，只能让它执行任务。执行任务了之后，它又有一些相关的记录的更改，那么这个 Agent 如果下次还需要更改，或者说有其他 Agent 需要它的帮助，那么这个 Agent 又可以被使用。所以说生命周期管理是一个很重要的。当下的全都是用 Context Comparator 重新组装，这样子每个是 Context Comparator，这个本来就有点黑箱以及规则主导。有些时候不是所有都能这么干的，而且性能消耗也比较大。所以说角色的生命周期管理以及选取策略编排是一个很重要的。然后 Context Comparator 应该下降为组装成一个新的 Agent，或者说旧的 Agent 达到了一定的使用上限，需要压缩，或者说重新产生一个新 Agent 的时候，甚至某些 Agent，它的身份，比如说负责某一个模块的更改，这个身份都可以不用变，然后部分的更改的历史记录也可以不用变。就这么直接用，可以复用一些部分，一些错误的一些可能导致误导的东西就可以不用 GPT 记成。所以这个生命周期以及 Context Comparator 这个过重的问题，也许是未来性能优化的一个点，也是我想到的一个点，而且这也符合人类管理的需求。到时候直接点角色卡片就可以知道它在干什么了。

### 当时回复

> 这个方向有道理，而且比单纯调整缓存更深入：把 Agent 当作可以持续管理、积累项目认识的工作主体，而不是每次任务都重新组装出来的一次性调用。但“文档完全没考虑、实现完全没有”还需要逐项核对，现有性能数据只能证明重复组装成本，不能单独证明生命周期缺失是全部根因。
>
> 你说的 Context Comparator，我理解是当前的 ContextCompiler。它的职责可以按下面这个方向重新划分：Role 定义职责、能力与权限；Agent 保留身份、负责范围、当前工作与积累的项目认识；Session 保存连续交互、探索过程、工具结果与执行上下文，并允许恢复、压缩或更换；生命周期与调度决定复用哪个 Agent、恢复哪个 Session，以及何时暂停、压缩、重建或退休；ContextCompiler 为首次启动、恢复、更新材料和压缩后重建提供上下文，而不是每次从头组装全部内容。
>
> Agent 身份可以稳定，Session 可以更换。比如“负责权限模块的 Agent”仍然是同一个工作主体，即使旧会话容量不足，也可以携带经过整理的工作记录进入新会话，不必丢失模块责任和历史脉络。
>
> 你的“探索本身就是 State 和记忆来源”也成立，但需要保留三个层次：工作状态保存探索文件、版本、进度和未解问题；可复用认识保存模块关系、已验证结论和失败尝试；完成、授权、正式决定等权威事实仍由对应模块的持久记录决定。Agent 记得某事，不代表该事实现在仍然有效。
>
> 复用策略也不应只看角色名称，应该综合负责范围、相关探索、来源版本、权限、忙闲状态和剩余上下文容量。ContextCompiler 仍然有用，但更多处理增量更新与必要重建，生命周期管理负责决定何时调用它。缓存也可以围绕稳定身份、稳定材料和连续会话组织起来。不过，复用 Session 不自动保证 99% 缓存命中；最终仍需检查实际发送给模型的内容是否保持可复用，以及新增内容所占比例。
>
> 角色卡片则可以成为这个模型的用户入口：看到它负责什么、正在做什么、最近探索到哪个版本、有哪些待处理事项，以及能否继续使用。
>
> 我会把这一方向归纳为后续架构优化的核心议题：稳定 Agent 身份、可恢复 Session、带来源的工作记忆、生命周期与选取调度，以及 ContextCompiler 的增量化和职责收缩。它与已经测出的重复来源检查、重复事实组装有关，但需要分别验证收益，不能只换一套对象名称就算解决性能问题。
